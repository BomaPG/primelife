**Step 5 — Track and Insights**:

- Track (`app/(tabs)/track/page.tsx`, `F6`) — the third tab, sibling to `home` and `move` under `(tabs)`. Fetches raw rows via the existing `dataAccess` range functions and hands them straight to the already-unit-tested pure functions in `lib/insights/derived` (`checkInStreak`, `hydrationStreak`, `movementStreak`, `getWeeklySummary`, `getTrends`) — this page adds no new derived-logic function, only fetching and rendering, per this step's explicit constraint. Renders three sections: Streaks (`F6-AC2`), "This week" (`F6-AC3`, same shape as Home's weekly summary, now including the walk distance Step 4 added), and Trends (`F6-AC4`) — water and walk-minutes as bar charts, sleep-quality as a plain three-line count list (a chart adds nothing over three numbers). A fourth section, Daily logs (`F6-AC1`), lists the last 7 local days newest-first, each showing water glasses, which meals were logged, sleep hours/quality, and walk count/minutes for that day — this is new UI-level grouping (filtering the fetched rows by date for display), not a derived-logic function, since Section 11 doesn't specify one for it.
- Streaks are computed over a wider 60-day range read (`STREAK_LOOKBACK_DAYS` in `track/page.tsx`), not the 7-day window the rest of the page uses — `checkInStreak`/`hydrationStreak`/`movementStreak` walk backward from today until the first gap with no upper bound, so feeding them only 7 days of rows would silently cap every streak at 7. `getWeeklySummary` and `getTrends` still receive the same wider arrays for water/walks/check-ins (harmless — both filter internally to their own 7-day window via `lastNDates`), so this doesn't cost a second read of those tables.
- `components/insights/WeekBarChart.tsx` — a small reusable 7-bar CSS chart (no charting dependency, per PRD Section 12's data-thrift guidance), used for both the water and walk-minutes trends. Bar height is relative to the week's own max (not a fixed scale), with a 4% floor so a zero day still renders a visible sliver rather than nothing; the full week's values are also exposed via `aria-label` on the chart container so the data isn't sight-only. Labels use `text-lg` throughout — the codebase's established C4 floor — rather than a smaller Tailwind size that would fall under 18px.
- `lib/content/mealTypeOptions.ts` (`MEAL_TYPE_OPTIONS`) — extracted from `MealsQuickLog.tsx`, which had this exact `{type, label}` array inline; Track's daily-logs view needed the same mapping to list which meals were logged each day, and duplicating the literal array a second time risked the two views' labels drifting apart. Both call sites now import the one array.
- Home (`app/(tabs)/home/page.tsx`) — added a "See streaks and trends" link under "This week", the same contextual-entry-point pattern Step 4 used for Move (no shared tab bar exists yet, so each tab is reached by a link from where it's contextually relevant rather than global nav).

**Step 4 — Walking Journal**:

- Move (`app/(tabs)/move/page.tsx`, `F5`) — the second tab, sibling to `home` under `(tabs)`. Owns today's walks + a week-scoped `getWeeklySummary` call in its own `reload()`, same pattern as Home. Renders the log-walk form, a list of today's walks (multiple per day, per the explicit constraint), and "This week" totals for walks/minutes/distance (`F5-AC2`). A static "Exercise library coming soon" line sits beneath the journal, per PRD Section 6's note that the Move tab may show one such line while that feature is deferred.
- `components/WalkLogForm.tsx` (`F5-AC1`) — required duration (minutes), optional distance (km) and note. Submit is disabled unless duration is a positive number and distance (if entered) is a non-negative number — mirrors the validate-before-write convention already used by `PreferencesFields`'s water target and `SleepQuickLog`'s hours field, rather than silently dropping bad input. Resets after each successful log so a second walk the same day is one more fill-and-submit, no extra navigation (multiple walks per day, no dedup key on `walks`).
- `lib/insights/derived.ts` — `WeeklySummary` gained `totalWalkDistanceKm` (sum of `distanceKm ?? 0` over the week's walks), alongside the `totalWalks`/`totalWalkMinutes` Step 3 already computed. Move calls the same `getWeeklySummary` Home uses, passing only the week's walks and empty arrays for the other categories, rather than introducing a second summary function — one pure function, two call sites each reading the fields they need.
- Home (`app/(tabs)/home/page.tsx`) — the Movement goal line now links to `/move` ("Log a walk"), and the "This week" walks line shows distance alongside minutes. No changes to Home's data-fetching: it already read `getWalks`/`getWalksInRange` into its own `reload()` in Step 3, so a walk logged on Move and a client-side navigation back to Home is enough to show it live — `F5-AC3` needed no new wiring on the Home side.

**Step 3 — Home, Daily Check-In, quick logs**:

- Home (`app/(tabs)/home/page.tsx`, `F3`) — replaces the Step 2 placeholder with the real dashboard. Owns all of today's + this week's data in one `reload()` that every write handler calls after its write, so quick-log changes reflect immediately with no page reload (F3-AC3). Renders: today's tip (`F3-AC1`), a check-in launcher or "Checked in today ✓", today's goals with live progress (`F3-AC2`, via `getTodaysGoals`), the three quick-log controls, a weekly summary (`F3-AC4`, via `getWeeklySummary`), and the daily affirmation (`F3-AC5`) — each read from local Dexie state only, no network call (`F3-AC6`).
- Daily Check-In (`components/CheckInModal.tsx`, `F2`) — one question at a time; tapping an answer immediately advances and auto-submits after the third, so completing it is exactly three taps with no separate submit tap (F2-AC5). Auto-launches from Home the first time a given local day is opened, unless already checked in or already dismissed that day (`F2-AC1`); dismissing doesn't relaunch it again the same day but leaves it reachable via a "Daily check-in" button (`F2-AC3`). Writes through the existing `completeCheckIn` (`F2-AC2`, `F2-AC4` — the streak itself is unchanged, already tested in Step 1).
- `lib/checkInDismissal.ts` (+ test) — small localStorage helper backing the "dismissed today" state. Deliberately outside Dexie/the data-access layer: it's UI session state, not app data, and the PRD fixes the Dexie schema exactly with no new fields allowed.
- Quick-log components (`components/quickLogs/{Water,Meals,Sleep}QuickLog.tsx`, `F4`) — presentational only; Home owns the data-access calls. Water is tap-to-increment/decrement (`F4-AC1`). Meals mark breakfast/lunch/dinner done with an optional note (`F4-AC2`). Sleep sets optional hours (on blur) and quality (on tap) via the same `upsertSleepLog` the check-in uses for quality — both key off `sleepLogs`' `date` primary key, so there is structurally one row per day regardless of which path writes to it (`F4-AC3`, and this step's explicit no-duplicate-rows constraint). No calorie/macro/weight field exists anywhere (`F4-AC4`).
