## What's built

**Step 9 — hardening pass** (this step): audited every route (Home, Nourish, Move, Track, Learn, Settings, plus onboarding) against `C1`/`C3`/`C4`/`C5` explicitly, not by assuming prior per-step verification generalized. Built a small reusable Playwright audit tool (not committed to the repo — lived in the QA scratch directory) that walks every visible element on a page and checks computed font-size (`C4`'s 18px floor), computed tap-target bounding box (`C4`'s 44px floor), and true WCAG contrast ratio (`C4`'s "high contrast"), across both light and dark `prefers-color-scheme`, over 18 distinct UI states per scheme (36 total) chosen to surface every conditional branch this step could find — modal steps, expanded note fields, filled forms, the Settings confirm-delete state, etc. — not just each route's default landing state.

- **C4 fix, checkbox tap targets (`app/onboarding/page.tsx`, `components/PreferencesFields.tsx`)**: every checkbox in the app (the onboarding disclaimer, the reminders opt-in, all 5 interested-topic checkboxes — used on both onboarding and Settings, since `PreferencesFields` is shared) rendered as a bare `h-6 w-6` (27px) box next to a separately-clickable `<label htmlFor>`, with neither independently reaching 44px and nothing joining them into one combined target. Restructured each from `<div><input/><label htmlFor="X">text</label></div>` to a single `<label htmlFor="X"><input/>text</label>`, styled `flex min-h-11 items-center gap-3`, so the whole row — including the gap between the box and the text — is one ≥44px clickable target. Verified live, not just measured: clicking the far end of the label's own text (nowhere near the checkbox) still toggles it, confirmed via two independent methods (a semantic Playwright click and a literal click on a specific word's own text-range rect).
- **C4 fix, standalone link tap targets**: `components/ReminderBanner.tsx`'s `href`-based CTA ("Log water", 88.9×31.5px measured), Home's "See streaks and trends" (208.3×31.5px), Nourish's "See also: ..."/"Read: ..." cross-links (321×31.5px), and `ArticleSection`'s "See meal ideas: ..." link all gained `flex min-h-11 items-center` — each is the sole content of its own row (no other text sharing that line), so none qualify for WCAG's inline-target exception the way two OTHER links deliberately don't get this treatment (see below). `ArticleSection`'s link happened to already measure ≥44px in the audit before this fix, but only because its specific article title text was long enough to wrap to two lines — an accidental pass that would have silently regressed the moment that copy got shorter; fixed for the same guaranteed reason as the others, not left to depend on copy length.
- **Deliberately left unfixed, and now says so in a code comment**: Home's "See meal ideas" (in the "Meals: 0/3 logged See meal ideas" list item) and "Log a walk" (in "Movement: No walk yet Log a walk") share their line with real sentence text — verified live via each link's own bounding rect vs. its `<li>`'s (22px tall, 4px inset within a 31.5px single-line row, with substantial non-link text preceding it on the same line) — the textbook case of WCAG's "target is in a sentence, constrained by the line-height of non-target text" exception. `/review`'s altitude-angle pass flagged that this distinction, while correct, had no in-code signal explaining why these two were skipped while five structurally-similar-looking links were fixed — added an explanatory comment directly above them so a future diff doesn't "fix" these into inconsistency with the rest of the app's inline-link convention, or assume they were just missed.

Deliberately touches nothing from `PushManager` — no subscription, no VAPID key, no server endpoint (`F9-AC4`, `C2`/SCOPE.md's "no backend of any kind"). Every function is safe to call unconditionally and never throws or rejects; none are ever awaited before rendering (`F9-AC3`).
- `lib/reminders/notifiedToday.ts` (new, + test) — a localStorage-backed "already notified today" flag per reminder kind, same rationale and shape as the existing `lib/checkInDismissal.ts` (disposable UI session state, not app data, so it deliberately sits outside Dexie and the `C6` data-access seam). Throttles the OS-level nudge to at most once per kind per day; the in-app banners are unaffected and just reflect current state on every render.
- `lib/reminders/copy.ts` (new) — draft banner and notification microcopy, addressing the PRD's `[PLACEHOLDER: insert - final reminder copy]` the same way Steps 6/7 addressed their own content placeholders: written, clearly flagged, not treated as final. See the review callout below.
- Home (`app/(tabs)/home/page.tsx`) — wired everything together. Two new `useEffect`s (both declared before the existing early return, alongside the pre-existing `reload()` effect, per the rules-of-hooks): one requests notification permission once profile resolves, only if `profile.remindersEnabled` and permission is still `"default"` (keyed only on `[profile]`, whose reference is stable across `reload()`s, so this doesn't re-prompt on every quick-log tap); the other fires at most one Web Notification per reminder kind per day when the same conditions the banners use are met. A third new effect runs a 15-minute `setInterval` purely to force periodic re-renders — see the bug-fix note below for why. Both new banners render conditionally at the top of the page, gated by `profile.remindersEnabled` — see the design-decision note below for why banners are opt-in-gated too, not just notifications.
- **Design decision, opt-in gates both surfaces, not just notifications**: `F9-AC2`'s "opts in" wording is written about the Web Notification permission request specifically; `F9-AC1`'s in-app-banner wording doesn't explicitly say it's opt-in. This step gates both behind `profile.remindersEnabled` anyway, because the existing preference checkbox's own label (`components/PreferencesFields.tsx`, unchanged) already reads "Send me gentle reminders to check in and drink water" — general, not notification-specific — so a user who unchecks it would reasonably expect no reminders of any kind, not just no OS notifications. Confirmed during `/review`'s removed-behavior pass as a spec nuance worth documenting, not a defect.
- **Bug found and fixed during `/review`, `lib/reminders/notifications.ts`**: `"serviceWorker" in navigator` only detects API *support*, not that a worker is actually registered and active. `navigator.serviceWorker.ready` resolves once one activates — but never resolves or rejects at all if none ever does. That's a real, reachable state: this project's own `next.config.ts` disables Serwist registration entirely in dev (`disable: process.env.NODE_ENV === "development"`), and a production registration can also fail silently (storage quota, a one-time install hiccup). Three independent review-agent angles converged on this same finding. Before the fix, `showReminderNotification` awaited `navigator.serviceWorker.ready` unconditionally and hung forever in that state — never falling through to the working plain-`Notification` fallback sitting right below it, with zero console error, silently defeating every future reminder for the rest of the session. Fixed with `getReadyServiceWorkerRegistration`, which races `.ready` against a 2-second timeout and returns `null` on timeout so the fallback path is actually reached. Reproduced the exact bug live and confirmed the fix (see "What's verified").
- **Gap found and fixed during `/review`, `app/(tabs)/home/page.tsx`**: `getReminders` was only ever recomputed when `todayState` changed (i.e., after a write-triggered `reload()`). A user who opens the app once in the morning, sees nothing due yet, and leaves the tab open without tapping anything would never see the hydration nudge even after crossing `HYDRATION_REMINDER_HOUR`, since nothing re-ran the check. Fixed with the `clockTick` state + 15-minute `setInterval` noted above, which forces a periodic re-render; the render body already recomputes `reminders` from a fresh `new Date().getHours()` on every render regardless of what changed. Confirmed live with Playwright's Clock API: fast-forwarding the virtual clock alone, with zero reload or interaction, correctly surfaces the hydration banner once both the reminder hour and one tick period have passed (see "What's verified").
- **Considered and left as-is**: the notification dedup mark (`markNotifiedToday`) is written synchronously *before* the fire-and-forget `showReminderNotification` call resolves, not after. Marking only after resolution was tried first (directly addressing a related, lower-severity review finding that a failed/hung attempt still gets marked as shown) but reverted: since the notification effect re-runs on every `reload()`/`clockTick`, marking-after left a real window for a second notification to queue if the effect re-fired (e.g. another quick-log tap) before a prior still-in-flight attempt resolved — a duplicate-notification bug traded for a "may not have visibly shown" edge case that's now rare anyway, since the SW-ready fix above bounds every attempt to a few seconds. `showReminderNotification`'s own degrade-silently contract (`F9-AC2`) already tolerates the residual case.
